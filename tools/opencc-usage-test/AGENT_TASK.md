# 测试任务：OpenCC 用量与扣费验收

给执行测试的 agent。按顺序完成，最后按“报告格式”交付。

## 目标

确认在真实部署 + 真实上游下：每次调用的 Token 数记得对、扣费算得对、余额扣得对、各处汇总一致、失败和限额场景行为正确。

## 你需要向人要的东西

只能从环境变量读取，**不要**写进文件、命令行参数、日志或报告：

| 变量 | 说明 |
|---|---|
| `OPENCC_BASE` | 站点地址，例如 `https://opencc.app` |
| `OPENCC_MEMBER_EMAIL` / `OPENCC_MEMBER_PASSWORD` | **专用测试成员**，余额 ≥ ¥2，测试期间没有别人用 |
| `OPENCC_ADMIN_EMAIL` / `OPENCC_ADMIN_PASSWORD` | 可选，只有跑 C7/C10 时需要 |

缺少前三个就停下来问人，不要用其他账号代替。

## 规则

- 只用专用测试成员。不要用真实成员的账号或密钥。
- 总花费上限 ¥2（脚本 `--max-spend` 默认 ¥2，到达即停）。不要调高。
- 不要修改站点设置、分组、渠道、上游账号。脚本只会创建并删除名字以 `usagetest-` 开头的临时密钥和临时成员。
- 某一项 FAIL 时继续跑完其他项，不要自己“修复”服务端，在报告里写清楚。
- 报告里不要出现任何密码、密钥、令牌。

## 步骤

### 1. 自动测试（必做）

```bash
cd OpenCC
python3 tools/opencc-usage-test/usage_test.py --report usage-test-report.json
```

如果人提供了管理员账号，再加跑 C7、C10：

```bash
python3 tools/opencc-usage-test/usage_test.py --with-admin --skip C1,C2,C3,C4,C5,C6,C8,C9 --report usage-test-admin.json
```

默认模型 `claude-sonnet-4-6`、默认用测试成员的第一个可用分组；人指定时用 `--model` / `--group-id`。要测其他模型就再跑一遍，换 `--model`。

### 2. 网页核对（必做，脚本做不到）

用测试成员登录网页：

1. 「用量明细」：最新几条记录的模型、Token 数、费用，与脚本输出的 C1/C2/C3 一致。
2. 「账户工作台」：今日消耗 = 今天所有记录扣费之和（包括测试前已有的记录）。
3. 用管理员登录后台（如果有）：「使用记录」能按测试成员筛出这些记录；仪表盘的今日实扣、账号成本、毛利在 1 分钟内更新，毛利 = 实扣 − 账号成本。

### 3. 与上游对账（有上游控制台权限时做）

1. 后台编辑上游账号，确认“上游ID”一栏已填写响应头名（通常是 `x-request-id`；留空表示不记录）。没填就记录下来，**不要自己改**，请人决定。
2. 挑 3 条测试记录，用上游请求编号在 SuperGPT 控制台找到同一次请求，核对输入、输出 Token 数是否一致。
3. 金额对比用 `deploy/opencc-cost-check.py`（见 `opencc-docs/11-团队自用与差价计费.md`）；这一步需要上游 Key，没有就跳过并在报告中注明。

## 怎么判断结果

| 用例 | 期望 | FAIL 通常意味着 |
|---|---|---|
| C1 普通请求 | 记录的 Token = 接口返回；扣费 = 标准费用 × 倍率；余额减少 = 扣费 | 用量解析或计费配置有误 |
| C2 流式请求 | 同上，且记录标记为流式 | 流式响应的用量解析有误 |
| C3 提示缓存 | 第一次有缓存写入、第二次有缓存读取，各按缓存单价计 | 缓存单价没配或被当普通输入计费 |
| C4 失败请求 | 返回错误、没有扣费、余额不变 | 失败请求被扣费 |
| C5 中途断开 | **只记录（INFO）**：断开后是否记录、扣了多少 | 无对错，写进报告供人判断 |
| C6 密钥额度 | 额度用完后返回 429 | 密钥额度不生效 |
| C7 余额不足 | 被拒绝；**WARN** 表示先透支了一次再拒绝 | FAIL = 余额不足仍能一直调用 |
| C8 汇总 | `/v1/usage` 今日请求数和金额 = 该密钥记录之和 | 汇总口径不一致 |
| C9 并发 | 10 个请求 → 10 条记录，余额减少 = 扣费之和 | 并发下漏记或重复扣费 |
| C10 隔离 | 其他成员看不到这些记录 | 越权查看 |

已知行为（不算缺陷，但要写进报告）：

- **C7 WARN**：Sub2API 放行请求只要求余额 > 0，费用事后结算，所以余额很低时会先透支一次（金额 = 那一次请求的费用），之后才拒绝。并发透支由在途预留拦住（C9 覆盖）。
- **C5**：客户端断开后，上游可能已经生成完，记录和扣费以上游实际返回为准。
